# Compiler build profiling

JFR-based profiling of the compiler build itself, to find compile-time
hotspots (e.g. in the monomorphization/specialization passes) and to catch
performance regressions as features land.

The process being profiled is the **boot compiler** — it is the JVM that runs
`--build idris2.ipkg`. To measure the cost of changes on your branch, the
flow is:

1. Build the compiler with your changes and install it as the boot compiler
   (or point `IDRIS2_BOOT` at it).
2. `./profiling/profile-build.sh -l my-change`
3. `./profiling/compare.py results/<baseline> results/<new-run>`

## Quick start

```sh
# Warm build (default): re-runs only the whole-program JVM codegen, where the
# monomorphization passes run. Fast; the right mode for regression checks.
./profiling/profile-build.sh -l baseline

# Full clean build (slow, also measures typechecking all modules):
./profiling/profile-build.sh -c -l clean-baseline

# Timing only, no JFR. Deep-stack sampling inflates wall clock (~80%
# observed), so compare wall times between -t runs and use profiled runs
# only to attribute the time:
./profiling/profile-build.sh -t -l timing-baseline

# Compare two runs (exits 1 on >10% wall-clock regression):
./profiling/compare.py profiling/results/<run-A> profiling/results/<run-B>
```

Requires JDK 21+ for the `jfr` tool (JDK 25 in use), and `python3`.

## What you get

Each run writes `profiling/results/<timestamp>-<sha>[-label]/`:

- `report.md` — wall time, phase split, hot-method tables, GC summary
- `report.json` — same data, consumed by `compare.py`
- `build.jfr` — raw recording; open in JDK Mission Control for flame graphs,
  or explore with `jfr view <view-name> build.jfr`
- `build.log` — make output

`profiling/history.csv` accumulates one row per run (timestamp, sha, mode,
wall seconds, jvm-backend sample share) for long-term trend tracking.

## How the report attributes time

Execution samples are bucketed by walking each stack leaf-to-root until a
domain frame is found:

| Bucket | Frames | Meaning |
|---|---|---|
| `jvm-backend` | `M_Compiler.M_Jvm.*`, assembler, ASM | monomorphization, type inference, codegen, bytecode assembly |
| `backend-common` | other `M_Compiler.*` | shared backend (CompileExpr, inlining, ANF) |
| `frontend` | `M_Core.*`, `M_TTImp.*`, `M_Idris.*`, `M_Parser.*` | parsing, elaboration, typechecking |
| `runtime/other` | nothing matched | runtime helpers, GC, I/O, JIT |

"Inclusive" tables count a sample for every distinct method anywhere in its
stack, so a method's % reads as "fraction of build time spent inside this
function or its callees". The `Top Compiler.Jvm.*` table is the one to watch
for monomorphization regressions (`inferDef`, `rewriteSpecCalls`,
`buildSpecialisationPlan`, ...).

## Notes

- Warm-mode numbers are comparable to other warm runs only; clean to clean.
  (`src/IdrisPaths.idr` is force-regenerated by make, so even a warm
  `make idris2-exec` re-runs the whole-program codegen every time.)
- The boot launcher hardcodes `-Xss92m -Xms3g -Xmx3g` *after* `JAVA_OPTS`,
  so heap size cannot be changed from here; check the GC section of the
  report to see whether the build is GC-bound.
- `-c` deletes `build/ttc` and `build/exec`.

# Typecheck workload & comparing against the Chez backend

A second harness measures **pure elaboration**: `idris2 --typecheck
idris2.ipkg` on a pristine copy of the compiler sources (304 modules, no
codegen). This is the workload where the JVM and Chez backends are directly
comparable, since both run the identical frontend on identical sources and
neither generates code.

## One-time setup: the Chez reference

```sh
brew install chezscheme
./profiling/setup-chez.sh          # ~20-30 min; creates ../idris-jvm-chez-ref
```

This builds a self-hosted chez-backend compiler from the **current commit**
in a git worktree, then typecheck-builds and installs prelude/base/linear/
network/contrib into the worktree's `bootstrap-build` prefix.

Why the script is not just `make bootstrap`: this fork's libraries contain
jvm-only `%foreign` specifiers. Specifier validation runs at **code
generation** time only, so the chez compiler typechecks all of them fine —
but `make bootstrap` builds libraries with `IDRIS2_INC_CGS=chez`
(incremental codegen), which fails on them. The script lets the bootstrap
fail after the compiler binary exists, then installs the libraries with
`IDRIS2_INC_CGS` unset. The same rule applies to anything you run under the
chez binary yourself: **keep `IDRIS2_INC_CGS` unset.**

The chez binary is a *yardstick*: its run-to-run variance is near zero
(single-threaded, CPU-bound), so it doubles as a sanity check on machine
conditions. It does not need rebuilding every commit — only when you want
the yardstick itself to include frontend changes.

## Timing comparison

```sh
./profiling/typecheck-compare.sh              # 2 interleaved rounds
./profiling/typecheck-compare.sh -r 3 -l after-my-change
```

Prints one line per run and writes
`profiling/results/<ts>-<sha>-tc-compare*/compare.log`. Runs alternate
chez/jvm so ambient load hits both sides; the 1-minute load average is
recorded before each run and runs starting above load 10 are flagged
`LOAD-POISONED?`.

**Measurement discipline** (hard-won; ignore at your peril):

- **Discard load-poisoned runs entirely** — do not average them in. A
  background build can turn a 350s run into 1650s.
- **Compare within a session, not across sessions.** Absolute numbers drift
  with ambient load/thermals; the chez column tells you whether conditions
  changed (it should sit near its usual value — if chez moved, the machine
  moved).
- **Never compare an isolated run against an in-suite run** (tests run with
  `--threads 10` and per-test times swing 2x under parallel load).
- Every run is a clean build (`rm -rf build` inside the workload copy);
  TTCs are never reused across runs or binaries.

## Stage-1 vs stage-2: what are you measuring?

A compiler built by the released boot (stage-1) *contains* your codegen
changes but its own bytecode was generated by the old compiler. To measure
how your codegen changes affect **compiler performance**, build stage-2:

```sh
IDRIS2_BOOT=~/bin/idris2-<release>/exec/idris2 ./mvnw package -DskipTests
cp -R build/exec /tmp/boot-stage1
IDRIS2_BOOT=/tmp/boot-stage1/idris2 ./mvnw package -DskipTests   # stage-2
```

Frontend-only changes (elaborator algorithms) are live at stage-1 already.

**TTC hygiene:** the TTC version has historically not been bumped between
releases, so different compiler builds share `build/ttc/<version>/` and
mixing them produces "Corrupt TTC data" mid-build. `rm -rf build/ttc`
whenever you switch which binary builds the compiler.

## Profiling the typecheck workload

```sh
./profiling/profile-typecheck.sh -l my-baseline
```

Runs a JFR-profiled clean typecheck (wall clock inflated by deep-stack
sampling — time with `typecheck-compare.sh`, attribute with this) and
writes:

- `cpu.md` — phase buckets + inclusive/leaf hot-method tables
  (same format as the build profiler above)
- `alloc.md` — allocation share by class and by (class, allocation site),
  from JFR's weighted allocation samples
- `typecheck.jfr` — raw recording for JDK Mission Control flame graphs

To find out *who drives* a hot method (e.g. why `Name.compare` is hot):

```sh
jfr print --events jdk.ExecutionSample <run>/typecheck.jfr \
  | python3 profiling/callers.py compare
```

`callers.py` skips generic plumbing frames (trampoline, currying, csegen,
Prelude fold bodies) so the answer is the elaborator-level driver; pass
`--raw` for immediate callers.

### Reading the reports — landmarks from past sessions

- `Runtime.tailRecFrame` inclusive % ≈ time spent inside mutually
  tail-recursive groups (the evaluator, `Name.compare`, termination
  checking). Its *leaf* % plus `tcGet`/`tcSet` is trampoline overhead
  proper; the rest is real work in the group bodies.
- `M__builtin.CONS` allocation is mostly `getFnArgs` argument spines and
  evaluator environments — frontend-algorithmic, not a codegen issue.
- `DirectMethodHandle.allocateInstance` = capturing-lambda allocation
  (largely Core-monad `>>=` closures).
- Chez reference numbers for context: chez typechecks this workload in
  ~175s on an M-series laptop; the JVM stage-2 compiler was at ~2.2x that
  before the trampoline-frame work and ~1.8-1.9x after (August 2026).
